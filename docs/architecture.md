# Архитектура Android-клиента Levik VPN

## Границы репозитория

Данный репозиторий содержит один основной компонент продукта: нативный клиент Android в каталоге `levik_vpn_android/`. Корневые файлы обеспечивают управление проектом, документацию релизов и CI-пайплайны.

Серверная часть, веб-сайт, Mobile BFF, Telegram-бот, база данных и инфраструктура развертывания являются внешними сервисами и не входят в состав репозитория. Модели API и пути эндпоинтов в коде Android описывают клиентский контракт взаимодействия.

## Архитектурные слои Android-приложения

Приложение разделено на независимые слои:

- **Пользовательский интерфейс (UI Layer)**: Jetpack Compose, Material 3, ViewModel и реактивное состояние (Kotlin StateFlow).
- **Сетевой слой (Network Layer)**: OkHttp, kotlinx.serialization, типизированные контракты Mobile API с валидацией схем ответов.
- **Аппаратная криптография (Security / Keystore Layer)**: генерация ключевых пар в Android Keystore (StrongBox / TEE) для идентификации устройства и подписи запросов (`X-Device-Signature`).
- **Локальное хранилище (Data / Storage Layer)**: EncryptedSharedPreferences и зашифрованная БД Room (AES-256-GCM) для безопасного хранения токенов и профилей.
- **VPN-сервис (VPN Core / Tunnel Layer)**: реализация `android.net.VpnService`, управляющая жизненным циклом сетевого туннеля и нативным процессом `libXray`.
- **Фоновые задачи**: WorkManager для фоновой синхронизации статуса подписки и проверки обновлений.

## Границы доверия и безопасность

- **Клиентское устройство не является доверенным авторитетом**: внешние серверные сервисы самостоятельно применяют проверки аутентификации, подписки и времени жизни сессий.
- **Входящие ответы API валидируются на границе слоев**: защита от поврежденных данных, инъекций и изменения формата.
- **Защита рабочих профилей VPN**: профили шифруются при сохранении, исключаются из логов и очищаются при выходе из аккаунта.
- **Обработка сбоев**: приложение корректно обрабатывает истечение сессий, отзыв устройств, смену сети (Wi-Fi ↔ LTE), перезапуск процесса и восстановление туннеля.

## Нативное ядро libXray

Файл `libXray.aar` является внешней бинарной зависимостью и исключен из Git. Скрипт `scripts/ci/fetch-libxray.sh` загружает официальный релизный архив `v26.7.28`, проверяет его SHA-256 хэш, извлекает AAR и повторно верифицирует его целостность перед сборкой.

## HotSwitch

Для совместимых обычных Xray-серверов ручной выбор меняет основной выход внутри работающего ядра. Уже открытые TCP/UDP-ассоциации сохраняют прежний выход; новые независимые соединения используют подтверждённый новый маршрут. TUN, foreground service, core lease, таймер и счётчики сессии сохраняются. Браузерные HTTP/2/HTTP/3 connection pools могут продолжать использовать старый выход. Потоки через упавший прежний сервер сохранить нельзя.

`SmartAutoLiveConfig` готовит ограниченный неизменяемый набор выходов и app-private Unix sockets с правами `0600`. Пул создаётся и для совместимого ручного подключения, независимо от режима Auto. Выключение Auto закрывает только автоматическую политику. В MVP ручной HotSwitch не применяется к LTE, Home Road, Game, отдельным TUIC/relay-движкам и изменившимся конфигурациям. Интерфейс показывает доступность конкретного перехода до нажатия.

`HotSwitchMainOwner` сериализует Manual и Auto. Перед ручным изменением проверяются реальный HTTPS-ответ размером 64 КиБ и DNS-ответ через тот же выход с настроенными резолверами. Записи MAIN и согласование сервисных правил ограничены бюджетом; потерянный ACK требует подтверждённой компенсации прежнего маршрута. Отмена сохраняет полученный ACK перед остановкой дальнейших policy writes. Если компенсация также не подтверждена, состояние `mainSelectionCertain=false` скрывает утверждение текущей страны и предлагает повторить выбор или явно переподключить всё.

`ServiceRouteRuntime` сохраняет собственные DNS/failure policies закреплённых сервисов. При изменении MAIN сразу согласуются `main`, `fallback=main` и прежние неподтверждённые записи; остальные правила продолжают работать. Устаревший цикл проверок не перезаписывает новый выбор и не завершает периодический монитор. После отмены и возобновления используется последний подтверждённый MAIN.

Сервис сравнивает выбранный сервер с точной установленной конфигурацией и актуальным авторизованным профилем, проверяет подписку, срок доступа, сеть и lease. Очищенный профиль не заменяется старой копией в памяти. OFF, revoke, teardown и смена сети инвалидируют ручной запрос. Команда «Переподключить всё» сначала проверяет наличие выбранной цели в свежем профиле, затем использует обычный путь переподключения. Она намеренно закрывает прежние потоки. Сбой сохранения локального предпочтения не выдаётся за сетевой отказ.

Unit-проверки выполняются для Direct и Play через `:app:testDirectDebugUnitTest` и `:app:testPlayDebugUnitTest`. `HotSwitchInstrumentedTest` проверяет настоящий JNI/libXray, private UDS, сохранение TCP/UDP и передачу 512 КиБ через локальные тестовые выходы с mux и без него. `HotSwitchUiInstrumentedTest` проверяет состояния реального Compose-компонента с синтетическими данными. Для изолированного запуска используется opt-in `-Plevik.testInstrumentationRunner=com.leviknet.vpn.HotSwitchTestRunner`: тестовый Application не запускает реальные sync/update workers. Обычный runner и production Application сохраняются.

Эти тесты работают без production-аккаунтов, публичных VPN-узлов и разрешения на системный VPN. Реальный Android TUN, физические Wi-Fi/LTE, фоновые ограничения OEM и конкретные звонки/игры требуют отдельной приёмки на устройстве.
