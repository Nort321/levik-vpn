# Модель безопасности Android-приложения Levik VPN

## Цели безопасности

- Защита ключей подписи Android, приватных ключей устройств, токенов сессий и рабочих VPN-профилей от случайного раскрытия и небезопасного сохранения.
- Аутентификация протокольных сообщений с использованием аппаратного ключа устройства и защита от атак повторного воспроизведения (replay protection) через метки времени и nonce.
- Изоляция сбоев на уровне VPN, сети, хранилища и UI без утечки чувствительных данных в системные логи.
- Прослеживаемость каждого артефакта сборки до проверенного коммита исходного кода, зафиксированных зависимостей и валидного сертификата подписи.
- Рассмотрение мобильного клиента как недоверенной среды при принятии решений об авторизации, правах доступа и отзыве сессий.

## Контроль репозитория

Репозиторий содержит исключительно код Android-клиента и доступен публике только для чтения и аудита. Issues, pull requests и внешние изменения отключены; публикация кода и релизов выполняется только владельцем. Скрипт `scripts/ci/check-repository-policy.sh` блокирует коммиты с приватными ключами, токенами, бинарными файлами, сессионными данными и неотслеживаемыми зависимостями. Все внешние действия в GitHub Actions зафиксированы неизменяемыми 40-значными SHA-хешами.

## Границы безопасности в приложении

- **Android Keystore (StrongBox / TEE)**: генерирует неизвлекаемые асимметричные ключи для подписи запросов к Mobile BFF (`X-Device-Signature`).
- **Шифрование данных в покое**: локальные данные шифруются через EncryptedSharedPreferences и зашифрованную БД Room. Логи, отчеты о сбоях и скриншоты не содержат токенов или VLESS-ключей.
- **Валидация сетевых данных**: все входящие ответы API строго валидируются по схеме перед передачей во внутренние слои приложения.
- **Безопасность VPN-туннеля**: параметры туннеля валидируются перед передачей в JNI-слой `libXray`. При сбоях соединение корректно разрывается без зависания интерфейса.
- **Play Integrity**: аппаратный аттестат устройства передается на сервер в качестве дополнительного сигнала безопасности.

## Цепочка поставок (Supply Chain Security)

- Нативное ядро `libXray.aar` загружается детерминированным скриптом `scripts/ci/fetch-libxray.sh` с двойной проверкой SHA-256 (архива и извлеченного `.aar`).
- Gradle работает в строгом режиме dependency verification: хэши всех разрешаемых артефактов закреплены в `gradle/verification-metadata.xml`, а версии — в lock-файлах.
- Процесс релизной подписи выполняется в изолированном GitHub Release Environment с ручным подтверждением владельца репозитория.
- Для каждой сборки формируется SBOM в формате CycloneDX/SPDX.
- Direct OTA использует два уровня ECDSA P-256 подписи: короткоживущий указатель версии и неизменяемый манифест APK. Клиент сохраняет максимальный проверенный `versionCode` и отклоняет rollback.
