# DNSTT / Яндекс DNS — Android pilot

## Назначение и состояние

Добавлена отдельная категория Android Direct «DNS · тест».
По указанию пользователя номер версии не меняется: 2.8.13 (99); задача завершается локальными коммитами.
Публичный релиз, постоянная установка узла и включение выдачи профилей ещё не выполнены.
Стабильный канал при проверке 2026-10-28 оставался на 2.8.13 (99).

Тестовый узел: `94.156.114.70`. Авторитетный DNS Beget подтвердил:

```
tns.levikfartik.ru. A 94.156.114.70
t.levikfartik.ru. NS tns.levikfartik.ru.
```

Внешний транспорт: только Yandex Basic UDP DNS `77.88.8.8:53` и `77.88.8.1:53`.
Второй адрес доступен отдельным резервным сервером в категории DNS. Автоматического
переключения на другого DNS-провайдера нет. Автовыбор обычного VPN не выбирает DNSTT.

## Реализация

- Официальный DNSTT `v1.20260501.0`, commit `0c5c52a57d899c05428c116898941761a2ed83c2`,
  локальный fork: `levik_vpn_android/native/dnstt/fork`. CC0 и оригинальные лицензии сохранены.
  Референс `dnstt-xyz/dnstt_xyz_app` изучен; его Flutter/runtime-бинарники не включены.
- Android защищает UDP-сокет от VPN и привязывает к выбранной физической сети через
  SCM_RIGHTS перед отправкой первого DNS-запроса. TUN, Kill Switch и правила приложений
  остаются у существующего Xray runtime.
- DNSTT → Noise → SOCKS5 с обязательным паролем → TCP egress. Ключ сервера закреплён
  в зашифрованном профиле. Чужой публичный ключ не даст расшифровать соединение.
- Авторизация берётся из синхронизируемого `/etc/levik-tuic/config.json`: UUID без дефисов
  и существующий пароль. Удаление/ротация записи закрывают активные потоки при следующем
  перечитывании (15 секунд **после обновления файла**, плюс задержка существующей TUIC sync).
  Отдельная новая база пользователей и миграция не нужны. Политика устройств наследуется
  от существующей выдачи профиля; сам SOCKS не вводит отдельный учёт физических устройств.
- Backend выдаёт DNSTT только клиенту с `X-Levik-DNSTT: 1`, Android metadata и уже выданным
  доступом к TUIC `94.156.114.70:8443`. Старые клиенты, Play и Game-only DNS не получают.
  Включение: `LEVIK_DNSTT_PUBLIC_KEY=<64 hex>` на `levik_vpn_air`; без переменной выдача выключена.
- DNS приложений перенаправляется в Xray DNS и идёт TCP через туннель к Яндексу.
  В unit прокси отдельный bind-mount `resolv.conf` также задаёт Яндекс; системный DNS
  хоста не меняется. UDP-трафик через DNSTT не поддерживается. Браузер может перейти
  с QUIC на TCP; звонки и игровые UDP-сессии этот режим не обслуживает.
- Прокси запрещает LAN, loopback, link-local, metadata, IPv6 transition addresses,
  SMTP и DNS к сторонним адресам. Разрешены TCP 53 (только Яндекс), 80, 443, 5222, 5223, 8443.
- Это тестовый транспорт с ограничением нагрузки. Его байты пока не экспортируются
  в биллинговый счётчик Remnawave; не продавать его как отдельный тариф с учётом трафика.

## Параметры первого пилота

| Параметр | Значение |
|---|---|
| Максимальный DNS UDP-ответ | 1232 байта; не увеличивать до 4096 |
| Лимит клиента | 40 запросов/с; старт 20, рост по 2/с |
| Ошибки / отсутствие ответов | снижение до 4 запросов/с; без накопленного burst |
| Допустимый диапазон профиля | 20–80 запросов/с; повышение только после замеров |
| Проверка транзакций | адрес резолвера, DNS ID и окно 5 секунд |
| Рукопожатие клиента / сервера | 25 / 30 секунд |
| Серверные сессии | не больше 10 одновременно |
| Потоки на туннель / пользователя | 16 / 16 |
| Общие подключения прокси | 96, включая неавторизованные |
| Прокси на пользователя | 64 КиБ/с суммарно в обе стороны |
| Общий приём DNS | 600 запросов/с, сверх лимита пакеты отбрасываются |
| Прокси idle / drain / lifetime | 90 секунд / 30 секунд / 1 час |
| Android health check | не чаще раза в минуту, таймаут 20 секунд |
| systemd DNS / proxy memory | 256 / 96 МиБ |
| systemd DNS / proxy CPU | 50% / 30% одного ядра |

Это собственные защитные ограничения пилота, **не опубликованные квоты Яндекса**.
Они не гарантируют отсутствие блокировки домена, IP или клиента. Безопасный для конкретной
сети темп требует длительных замеров. Все пользователи делят один домен и агрегированную
нагрузку резолвера. Скорость DNSTT не следует сравнивать с обычным VLESS/QUIC.

## Проверено 2026-10-28

- DNS-делегирование у `ns1.beget.ru` и A-запись `tns`.
- Независимый сервер → каждый Yandex DNS → узел: 32 КиБ с точным сравнением содержимого.
  При фиксированных 40 запросах/с: 14,47 КиБ/с (77.88.8.8), 8,63 КиБ/с (77.88.8.1).
  Это короткий пробный обмен, не устойчивый throughput и не результат мобильной сети.
- Финальный адаптивный клиент/ограниченный сервер + авторизованный прокси:
  HTTPS example.com с проверкой TLS-сертификата и TCP DNS через оба резолвера;
  неверный пароль отклонён. HTTPS-тест с handshake: около 3,3–3,7 секунды.
  Эти авторизованные проверки выполнялись с самого тестового узла через Яндекс.
- С текущего Mac UDP-проверки завершились таймаутом. Локальные UDP DNS-ответы выглядят
  перехваченными; не считать это доказательством работоспособности сети телефона.
- Android Direct и Play unit tests, Direct lint и сборка debug APK прошли.
- 54 backend-проверки выдачи профиля/TUIC/DNSTT, TypeScript, ESLint и Next.js build прошли.
- 8 Python-тестов прокси: обязательная авторизация, неверный пароль, отзыв активной сессии,
  закрытие доступа при повреждённом файле, запрет metadata/LAN/UDP/чужого DNS.
- Go `test -race ./...` прошёл. `go vet` новых client/server пакетов прошёл.
  Полный upstream `go vet ./...` сообщает о двух существующих вызовах `testing.T.Fatal`
  из goroutine в `noise/noise_test.go`; runtime этих файлов не содержит.
- Android native ABI: arm64-v8a, armeabi-v7a, x86_64, ELF PIE с 16 КиБ LOAD alignment.
  Native SBOM включает DNSTT; release workflow policy проходит.

Физический Android не подключён. Не проверены: реальная мобильная сеть/белые списки,
Wi-Fi↔LTE handover, Doze, сутки работы, длительная нагрузка 10 клиентов, подписанный
release APK/OTA и полный corresponding-source из чистого release commit.

## Установка и включение

1. Собрать Linux amd64 `./dnstt-server` из того же fork Go 1.26.9, `CGO_ENABLED=0`.
2. В новый staging-каталог узла передать бинарник, `proxy.py`, `resolv.conf`, два unit-файла
   и `install.sh` из `levik_dnstt/server`. Сверить SHA-256 с локальной сборкой.
3. Остановить временные probe/pilot units этой задачи, если они ещё запущены.
4. Запустить `install.sh`. Он проверяет точный IP, свободные порты, Python >=3.11,
   существующий TUIC access file, отсутствие всех целевых файлов; перезапись запрещена.
   Цели: `/opt/levik-dnstt/releases/20261028-pilot1`, `/etc/levik-dnstt`, два новых systemd units.
   Открывается только UDP 53 на указанном IPv4; systemd-resolved остаётся на loopback.
5. Проверить HTTPS/DNS/отказ неверному паролю, затем выставить публичный ключ в backend.
   Приватный ключ остаётся на узле и передаётся DNSTT через systemd LoadCredential.
6. В отдельной задаче выбрать следующий номер, собрать/подписать обычным Android release
   workflow, проверить на телефоне и опубликовать тестовую возможность в Direct.
   Текущая задача ограничена локальными коммитами; push и публикация не выполняются.

Постоянная установка не была выполнена: защитный hook отклонил первоначальную запись
в `/opt` как потенциальную перезапись. Представленный first-install script подготовлен
для отдельного подтверждения. Автоматическая проверка также отклонила перенос временных
тестовых паролей на второй сервер; вместо этого пароли оставались только на тестовом узле.

Откат: убрать `LEVIK_DNSTT_PUBLIC_KEY` и пересобрать backend; запустить `rollback.sh`
на узле. Он выключает только DNSTT units и его UDP 53 rule, сохраняя ключи и release-файлы.
Обычные VPN-протоколы и их конфигурации не изменяются установкой DNSTT.
